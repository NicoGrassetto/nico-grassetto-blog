Programs work with values in memory, but files and network connections carry text or bytes. **Serialisation** turns those values into a representation that can be stored or sent elsewhere. **Parsing** reads the syntax of a representation into a structure the program can work with. Reconstructing language values or application objects is called **deserialisation**; JSON libraries often handle parsing and deserialisation in the same call.

After receiving a JSON request, a service parses it before using its fields. Before sending a response, it serialises its data back into JSON. The same boundary exists when reading and writing a file.

<SerialisationDiagram />

JSON is the example here, not a requirement of either operation. Other formats include XML and Protocol Buffers. JSON itself has objects, arrays, strings, numbers, booleans and `null`; each programming language maps these to its own types.

## Parsing a string

Consider an order sent by an online shop:

```json
{ "id": 42, "item": "book", "quantity": 2 }
```

In this form, the order is text. Parsing it gives the application a structured value whose `quantity` field it can read. Each example below prints `2`.

```java
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.node.ObjectNode;

public class Parse {
```

```java
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.node.ObjectNode;

public class Serialise {
    public static void main(String[] args) throws JsonProcessingException {
        ObjectMapper mapper = new ObjectMapper();
        ObjectNode order = mapper.createObjectNode();
        order.put("id", 42);
        order.put("item", "book");
        order.put("quantity", 3);

    }
}
```

## Reading and writing JSON files

Files add an input/output step, but the conversion is the same: read the representation, parse it, change a value, then serialise the result.

Save the `order.json` tab in your working directory. Each program reads that file, changes the quantity from two to three, and writes `updated-order.json`. The output is indented to make it easier to read; indentation is a presentation choice, not a different data format.

```go
package main

import (
    "encoding/json"
    "log"
    "os"
)

func main() {
    input, err := os.ReadFile("order.json")
    if err != nil {
        log.Fatal(err)
    }
    var order map[string]any
    if err := json.Unmarshal(input, &order); err != nil {
        log.Fatal(err)
    }
    order["quantity"] = 3

    output, err := json.MarshalIndent(order, "", "  ")
    if err != nil {
        log.Fatal(err)
    }
    if err := os.WriteFile("updated-order.json", output, 0600); err != nil {
        log.Fatal(err)
    }
}
```

```java
public class FilesExample {

        ObjectNode order = mapper.readValue(new File("order.json"), ObjectNode.class);

}
```

A missing file and malformed JSON are different failures: one concerns reading the data, the other concerns its contents. These examples stop on either failure. In an application, handle the specific error at the boundary rather than continuing with missing or partially parsed data.

## Serialising objects

A language object is not automatically a JSON object. Dates, decimal values and custom classes may need an explicit conversion or a library-specific mapping. Decide what the representation should contain before choosing how to encode it.

<div class="table-scroll" role="region" aria-label="JSON representations for application values" tabIndex={0}>

| Application value | Possible JSON representation            | What to agree on                       |
| ----------------- | --------------------------------------- | -------------------------------------- |
| Date and time     | An ISO 8601 string                      | Time zone and precision                |
| Money             | Integer minor units or a decimal string | Currency, scale and rounding           |
| Custom object     | An object containing selected fields    | Field names, types and optional values |

</div>

Number ranges also differ between languages. A large integer that one program stores exactly may lose precision in another; identifiers can be represented as strings when their exact digits matter.

Finally, **valid JSON is not necessarily valid application data**. An order with quantity `-1` can be perfectly valid JSON and still be an invalid order. Check required fields, expected types and business rules after parsing.

## Beyond JSON: Protocol Buffers

Parsing and serialisation are not specific to JSON. XML (`.xml`) and YAML (`.yaml`) are other text formats; CSV (`.csv`) stores rows and columns. Protocol Buffers, MessagePack and CBOR use binary encodings. Each format has its own rules and libraries, but the job is the same: convert application values into a representation, then read that representation back.

Other formats include BSON, Apache Avro, FlatBuffers and Apache Parquet.

**Protocol Buffers**, or **Protobuf**, describes messages in a `.proto` schema. The schema below represents the same order used throughout this article. The numbers `1`, `2` and `3` identify the fields in the binary message; they are not default values.

Unlike JSON, the binary message does not include field names such as `quantity`. A reader uses a compatible schema to interpret the numbered fields. Keep existing field numbers stable when changing the schema, and reserve the numbers of fields you remove rather than reusing them.

Save the shared `order.proto` tab alongside the example for your language. Each program creates an order, **serialises it into bytes**, then **deserialises those bytes into a new message** and prints its quantity. There is no JSON conversion in this round trip.

### Go

In a new directory, run `go mod init example.com/orders`, then `go get google.golang.org/protobuf@v1.36.10` and `go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.10`.

With the Protocol Buffers compiler (`protoc`) installed and `protoc-gen-go` on your `PATH`, run `protoc --go_out=. --go_opt=module=example.com/orders order.proto`. This creates the `orderpb` package. Save this example as `protobuf.go` and run `go run protobuf.go`.

```go
package main

import (
    "fmt"
    "log"

    "example.com/orders/orderpb"
    "google.golang.org/protobuf/proto"
)

func main() {
    order := &orderpb.Order{Id: 42, Item: "book", Quantity: 2}
    encoded, err := proto.Marshal(order)
    if err != nil {
        log.Fatal(err)
    }

    var decoded orderpb.Order
    if err := proto.Unmarshal(encoded, &decoded); err != nil {
        log.Fatal(err)
    }

    fmt.Printf("%x\n", encoded)
    fmt.Println(decoded.GetQuantity())
}
```

### Java

Reuse the earlier Gradle project and add `implementation 'com.google.protobuf:protobuf-java:4.33.0'` to its `dependencies` block. With `protoc` version 33.0 installed, run `protoc --java_out=src/main/java order.proto` from the project directory.

Save this example in `src/main/java/ProtobufExample.java` and run `gradle run -PmainClass=ProtobufExample`. The compiler and runtime versions must be compatible; the versions above work together.

```java
import java.io.IOException;
import java.util.HexFormat;
import example.orders.OrderSchema.Order;

public class ProtobufExample {
    public static void main(String[] args) throws IOException {
        Order order = Order.newBuilder()
            .setId(42)
            .setItem("book")
            .setQuantity(2)
            .build();

        byte[] encoded = order.toByteArray();
        Order decoded = Order.parseFrom(encoded);

        System.out.println(HexFormat.of().formatHex(encoded));
        System.out.println(decoded.getQuantity());
    }
}
```

<div data-code-file="schema" data-code-label="order.proto">

The Go and Java options control where their generated code lives. They do not change the message's binary format.

```protobuf
syntax = "proto3";

package orders;

option go_package = "example.com/orders/orderpb";
option java_package = "example.orders";
option java_outer_classname = "OrderSchema";

message Order {
  int32 id = 1;
  string item = 2;
  int32 quantity = 3;
}
```

</div>

</CodeWorkspace>

For this message, the examples print the encoded bytes in hexadecimal, followed by the restored quantity:

```text
082a1204626f6f6b1802
2
```

The hexadecimal line is just a readable display of the bytes, not the format you need to store or send. Protobuf does not guarantee a single byte ordering across implementations or versions; what matters is that a compatible reader reconstructs the same values.

To save the message as `order.pb`, write `encoded` as binary data. Read the file as bytes and pass those bytes to the decoder; do not treat it as UTF-8 text. The filename extension is a convention, not what determines the encoding.

The same bytes can also travel over a network. Protobuf does not require gRPC or a particular web framework; [this Express example](https://compile7.org/serialize-and-deserialize/how-to-serialize-and-deserialize-protobuf-in-expressjs) shows the HTTP version of that boundary.

A schema describes field types, not every rule of your application. This schema still allows a negative quantity, and successful decoding does not prove that the bytes were intended to represent an order. Validate the decoded values before using them.
